    # 产品需求文档 (PRD)：建筑 AI 方案预审与图纸资料协同多 Agent 工作台

## 1. 文档概述
*   **项目名称**：建筑 AI 方案预审与图纸资料协同多 Agent 工作台（代号：Arch-Harness）
*   **文档版本**：V1.3（收敛站内协同，预留飞书接口）
*   **文档状态**：待评审
*   **目标读者**：产品团队、研发团队（前端/后端/算法）、UI/UX 设计师、建筑业务专家

## 2. 背景与产品定位
**2.1 业务背景**
建筑设计院在方案设计与施工图阶段，面临海量图纸的交叉审阅。传统的人工审图存在“错漏碰缺”发现率低、多专业（建筑、结构、机电）协同周期长、规范查对耗时等痛点。

**2.2 产品定位**
基于 Harness Engineering 架构的 AI 智能审图与协同平台。通过多 Agent 协作，自动解析图纸、识别规范冲突、生成预审报告，并推动跨专业的设计协同。

**2.3 核心演进策略**
*   **V1.0 (MVP 阶段)**：聚焦单一核心用户，打通“上传-预审-站内通知-输出报告”闭环。
*   **V1.5**：接入外部 IM（如飞书）提升协同触达率。
*   **V2.0**：接入 RBAC 权限模型，开放多角色视图。

## 3. 用户画像与核心痛点 (V1.0 阶段)
| 角色 | 核心诉求 | 当前痛点 |
| :--- | :--- | :--- |
| **主创建筑师** | 方案快速自查、减少返工 | 缺乏专业审图经验，人工核对耗时，容易遗漏规范 |
| **图纸校对专员** | 提升审图效率、多专业协同 | 人工“找茬”极易疲劳；跨专业图纸冲突（如管线打架）难以肉眼识别 |

## 4. 核心业务流程 (V1.0)
1.  **上传与解析**：用户在工作台创建项目，上传图纸文件（**仅限 PDF 或 DXF**）。
2.  **任务分发**：系统自动将图纸交给多个专业 Agent 并行处理。
3.  **AI 预审执行**：规范、一致性、碰撞等多 Agent 并行审查。
4.  **报告生成与批注**：生成预审报告，并在图纸上精确定位问题。
5.  **站内协同与闭环**：审核专员在系统内将批注指派给对应设计师；**系统触发站内消息通知**；设计师登录系统查看批注，修改图纸后重新上传复核，直至问题关闭。

## 5. 功能需求详细说明 (V1.0 MVP 版本)

### 5.1 工作台首页 (Dashboard)
*   **任务概览**：待审核图纸数、已发现问题数、本周 AI 拦截率。
*   **待办中心**：展示当前用户待处理的批注任务、待复核的图纸。
*   **快捷入口**：新建项目 / 上传图纸 / 最近打开的项目。

### 5.2 智能预审中心（核心）
*   **文件上传模块**：
    *   支持拖拽上传，大文件断点续传。**格式仅限 `.pdf` 和 `.dxf`**。
    *   **格式严格校验**：拦截非标格式并提示“当前版本仅支持 PDF 与 DXF”。
*   **多 Agent 解析引擎**：
    *   **PDF 解析**：采用 OCR + 版面分析提取文本和图框信息。
    *   **DXF 解析**：利用开源库（如 `ezdxf`）提取图层、实体、块引用及坐标信息，还原图纸拓扑结构。
    *   **Harness 上下文管理**：确保 Agent 能正确读取解析后的元数据（图层、标高、尺寸等）。
*   **预审报告展示与导出**：
    *   列表视图（按等级/专业分类）与图纸联动视图（点击问题项高亮定位）。
    *   支持一键导出 PDF 或 Excel。

### 5.3 协同批注与流转（纯站内闭环）
**5.3.1 批注工具**
*   支持在图纸上手动添加红框、文字批注，支持指派给项目内成员。

**5.3.2 状态管理**
*   问题状态流转：`待确认` -> `已下发` -> `已修改待复核` -> `已关闭`。
*   支持批量操作状态变更。

**5.3.3 站内消息通知（V1.0 唯一触达渠道）**
*   **触发事件**：AI 预审完成、批注被下发、批注待复核。
*   **触达方式**：
    *   **顶部导航栏红点/未读角标**。
    *   **站内消息中心列表**（点击消息自动跳转至对应图纸和批注位置）。
*   **技术架构（预留飞书接口设计）**：
    *   业务层发布领域事件（如 `AnnotationStatusChanged`） → 消息队列异步消费 → 统一 `NotificationService` 处理。
    *   `NotificationService` 采用**适配器模式（Adapter）**。V1.0 仅实现 `InAppAdapter`（写库站内信）；V1.5 只需开发 `FeishuAdapter`（调用 Webhook）即可无缝接入，无需改动业务代码。
    *   数据库预留 `user_notification_preferences` 表，用于后期配置用户的飞书 Webhook 地址或群组绑定。

### 5.4 系统管理（V1.0 基础版 & V2.0 预留）
*   **用户管理**：基础的注册、登录。
*   **项目管理**：创建项目、分配项目成员（邀请制）。
*   **权限架构设计（研发重点）**：
    *   数据库设计必须包含 `Role` 和 `Permission` 表（用户模型预留 `Admin`、`Reviewer`）。
    *   前端路由预留：菜单栏根据角色权限动态渲染。

## 6. 非功能需求
*   **性能要求**：单张 A1 图纸 PDF 解析 < 1 分钟；DXF 解析 < 3 分钟。前端图纸渲染加载 < 3 秒。
*   **站内消息要求**：事件触发后，站内信写库及前端红点更新延迟 < 1 秒。
*   **安全与隐私**：图纸文件加密存储；支持本地化/私有云部署（满足设计院对图纸资产极度敏感的需求）。
*   **AI 准确率目标**：预审问题召回率 ≥ 85%，误报率 ≤ 15%。

## 7. 数据埋点与指标定义
*   **北极星指标**：AI 拦截的有效设计缺陷数量。
*   **过程指标**：
    *   周活跃审图专员数（WAU）。
    *   AI 报告采纳率（用户标记为“已确认”的问题占 AI 输出总问题的比例）。
    *   **站内信触达率**：站内信已读率、从消息点击跳转至图纸的转化率。

## 8. 风险与应对机制
*   **风险 1：AI 误报率过高导致用户放弃使用**。
    *   *应对*：增加“用户反馈”按钮（👎 踩/误报）；初期以“高召回、宁多勿漏”为主，人工二次确认。
*   **风险 2：不直接支持 DWG 格式带来的用户流失风险**。
    *   *应对*：前端提供详尽的“DWG 转 DXF 一键操作指南”。V1.5 版本再引入商业组件支持原生 DWG。
*   **风险 3：DXF 文件过大导致解析超时**。
    *   *应对*：采用流式/分块解析；前端限制单个 DXF 文件最大体积（如 50MB）。
*   **风险 4：纯站内信导致用户触达率低（用户不登录就不知道有新任务）**。
    *   *应对*：这是 MVP 阶段的妥协。通过每日邮件摘要（可选降级方案）或后续快速接入飞书 Webhook 来解决。**V1.0 务必把 `NotificationService` 和飞书接口预留好，这是核心架构要求。**

## 9. 附录：研发架构特别说明 (Harness Engineering 落地)
*   **Agent 编排层**：采用 LangChain / AutoGen 等框架。
*   **DXF 解析技术选型建议**：
    *   **Python 生态**：推荐使用 `ezdxf` 库提取图层、块信息，喂给大模型。
    *   **解析重点**：提取“图框信息”和“特定图层（墙体、门窗）”，非全量解析。
*   **【新增】通知模块适配器设计说明**：
    ```python
    # 伪代码示例
    class NotificationService:
        def __init__(self):
            self.adapters = [InAppAdapter()] # V1.0 仅站内
            # self.adapters.append(FeishuAdapter()) # V1.5 预留

        def send(self, event):
            for adapter in self.adapters:
                adapter.send(event)
    ```
    这样设计确保 V1.5 接入飞书时，只需实现 `FeishuAdapter` 并在配置中开启即可。
